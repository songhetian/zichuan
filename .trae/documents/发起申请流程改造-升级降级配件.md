# 发起申请流程改造（升级/降级配件）

## Context（背景）
当前"升级配件"(ASSET_UPGRADE)申请由发起人填写：设备(全部可选) → 旧配件型号(modelId，限该设备现有配置) → 新配件型号(newModelId，全部型号可选) → 原因。审批通过后 `approval-execute.ts` 自动执行配件更换（预占→扣库存→删旧/upsert新→资产释放→流水/日志）。

用户已确认新流程，发起人只需：
1. **设备**：仅本人名下设备中选择；本人名下只有一个在用设备时**自动带出**，无需手选。
2. **配件类别**：仅显示**该设备已有的配件**（Asset→AssetComponent→ComponentModel.category）。
3. **动作**：仅 "升级 / 降级"。
4. **原因**。

不再填旧配件、也不再填新配件型号。配件的实际更换/增加/减少由**资产管理员（设备管理员）部门后续执行**。

涉及跨前后端：提交 payload 结构、提交校验、表单、审批详情展示，以及**执行端**（原依赖 modelId/newModelId 自动换配件）。

---

## 1. 新 payload 结构（ASSET_UPGRADE）
`src/lib/approval-execute.ts` 的 `upgradePayloadSchema` 改为：

```ts
z.object({
  assetId: z.number().int().positive(),
  componentCategoryId: z.number({ required_error: "配件类别不能为空" }).int().positive(),
  action: z.enum(["UPGRADE", "DOWNGRADE"]),
  reason: z.string().min(1, "申请理由不能为空"),
})
```

提交端校验（`src/actions/approval.actions.ts` 原 modelId 校验处）：
- 设备存在、未被预占、归属本人（沿用现有）。
- 删除原"旧配件 modelId 在该设备上"校验，改为：`componentCategoryId` 须存在于该设备现有配件——查 `assetComponent.findMany({where:{assetId}})` 关联 `.model.categoryId` 集合，若不包含则报"该设备不存在该配件类别"。

## 2. 执行端（推荐方案 a）
**审批通过仅释放预占＋记日志，不再自动改库存/设备配件。**
理由：发起人不提供新/旧型号，自动执行缺关键入参（新件是哪个、增/减数量）。实际更换由资产管理员后续手工完成（本次**不做**资产管理员执行界面）。

`executeUpgradeOnApproval` 精简为：校验 payload 通过 → 写 `lifecycleLog`（如 action=COMPONENT_CHANGE_APPROVED，remark 含设备/类别/动作/原因）→ 释放资产（恢复 `reservedFromStatus`、清预留字段）。不再操作 `componentStock / componentStockLog / assetComponent`。

对现有 DB 测试的影响（需同步改）：
- "自动执行升级（扣库存/换配置/回旧件/流水）"（tests/approval-engine.test.ts 约 L550-611）→ 改为断言：库存不变、旧配置仍在、无 UPGRADE_USE/RETURN 流水、仅 EXECUTE/COMPONENT_CHANGE_APPROVED 日志 + 资产已释放。
- "库存不足 → EXECUTE_FAILED"（约 L613-654）→ 删除或改为"审批通过即释放"用例（已无自动扣减）。
- 其余引用了 `newModelId` 的断言同步更新。

## 3. 前端表单与页面数据
`src/app/(main)/approvals/new/page.tsx`：
- `assetComponents` 读取改为 `include:{ model: { select:{ id,name,brand, category:{ select:{ id,name } } } } }`，map 输出 `{assetId, categoryId, categoryName}`（升级不再用全部 models，可保留供不碍事或删除）。

`src/app/(main)/approvals/new/new-request-client.tsx`：
- **单台自动带出**：`useEffect`，当 `bizType==="ASSET_UPGRADE" && assets.length===1` 时 `setAssetId(String(assets[0].id))`（并纳入切换业务类型时的重置逻辑）。
- 由 `currentComps` 派生 `currentCats`（对 `{categoryId,categoryName}` 去重）作为"配件类别"下拉数据（无设备时禁用）。
- 新增"动作"下拉（升级/降级），删除"旧配件型号""新配件型号"两个下拉。
- 提交 payload 组装为 `{ assetId, componentCategoryId, action, reason }`；标题 placeholder 改"如：申请升级内存"。
- 校验更新：选设备、选配件类别、选动作。
- 报废(ASSET_SCRAP)分支保持不变。

## 4. 审批详情页展示
`src/app/(main)/approvals/[id]/approval-detail-client.tsx`：原展示"设备编号 / 新配件型号"（解构 `newModelId`）改为展示 **设备（assetNo·name）/ 配件类别（categoryName）/ 动作（升级/降级）**。建议在 `page.tsx` 提交时把可读名快照写进 payload（如 `assetNo/assetName/categoryName`），详情页直接展示。

## 5. 需同步的测试
- `tests/approval-engine.test.ts`：`upgrade` 对象改 `{assetId, componentCategoryId:<catId>, action:"UPGRADE", reason}`；同步由此对象派生的提交/预占/流转/越权/列表用例；改写/删除两条自动执行用例；"缺旧配件"改"缺配件类别/动作"。
- `tests/approvals-client.test.tsx`：首条交互用例由"选旧/新配件"改为"选配件类别+选动作"，并断言新 payload；详情展示用例同步。
