# 审批通过后的落地执行：从写死 ASSET_MANAGER 改为由流程末节点角色驱动

## Context（背景与目标）

现状 `/approvals/execute`「待执行变更」被**硬编码**为：仅当单子满足
`status=APPROVED`、`businessType∈{升级/更换/维修}`、`finalNodeRole=ASSET_MANAGER`、`executedAt=null`
才进入执行。同时 `workflow.actions.ts` 的 `ensureAssetManagerFinalNode` 强制升级单末节点必须是资产管理员角色。

问题：一旦某业务流程的**最后一个审批节点不是资产管理员**，或系统里**根本没有 `ASSET_MANAGER` 角色**，
审批通过后的单就卡死在 APPROVED，无人能在 execute 执行落地。

目标（已与用户确认）：
- **轻量解绑**：不改数据模型、不加节点"执行动作"字段。
- **末节点审批角色即执行人**：谁拥有末节点配置的角色，谁就负责执行落地。
- 升级/更换/维修仍走 execute 页手动执行（权限动作不变）；自动执行（报废/退回）与交接单（离职）不受影响。

## 改动点

### 1. 放开 node 末节点强制（`src/actions/workflow.actions.ts`）
- 移除 `ensureAssetManagerFinalNode` 及其对 `ASSET_UPGRADE` 末节点必须 `ROLE + ASSET_MANAGER` 的强校验，清理其调用点；若 `defaultAssetManagerNode` 不再被引用一并删除。
- 保留 `validateNodeFields` 基础字段校验。
- 新增**软校验**（仅提示不阻断）：需手动执行的业务类型，末节点应为 `assigneeType=ROLE` 且 `assigneeRole` 非空——避免具体用户型末节点导致后续无法匹配（见风险 1）。

### 2. execute 准入改为「末节点角色」匹配（`src/actions/approval-execute.actions.ts`）
新增 helper 取当前用户角色 key：
```
getRoleKey(user.id) → 查 prisma.admin.role.key；无角色返回 null
```
把所有硬编码 `finalNodeRole: "ASSET_MANAGER"` / `!== "ASSET_MANAGER"` 替换为「当前用户角色」：
- 列表 `getPendingExecutionRequests`（~L169）：`finalNodeRole: roleKey` → 列表天然只展示当前用户角色能执行的单。
- `getExecutableDetail`（~L284）：`finalNodeRole !== roleKey` → 拒绝。
- `executeApprovedChange / executeReplaceChange / executeRepairChange`（~L71/429/556）：`where.finalNodeRole: roleKey` → 只能执行自己角色维度的单。
- 自动执行/交接单的单 `finalNodeRole=null`，`where.finalNodeRole=<role>` 天然跳过，无需特殊处理。

### 3. execute 前端准入（`src/app/(main)/approvals/execute/execute-client.tsx`）
- 服务端列表已按角色过滤，不再需要 `usePermission("asset.upgrade.execute")` 拦截执行按钮。
- 建议：删除该前端权限门槛（改动最小）；或由 execute 服务端页面传入 `userRole` prop 供前端比较。保持页面整体可达。

### 4. 服务端权限校验调整（同 `approval-execute.actions.ts`）
- 移除 action 内 `guardPermission(user, "asset.upgrade/…execute")` 的**强制**拦截，改为「角色匹配优先」。
- 原因：`guardPermission` 依赖权限点授予；若某环境未给新末节点角色授予对应权限点，会误拦本应放行的执行者。权限点仍保留在 `permissions.ts`/角色矩阵中，作为未来可选收紧，不在 action 内强制。

## 风险与处理

1. **末节点为具体用户（`assigneeType=USER`）**：`assigneeRole` 为空 → `finalNodeRole=null` → 该单任何角色都无法匹配（安全但成孤儿）。处理：靠改动点 1 的软校验在发起时提示此类末节点不可执行；本期**只支持角色型末节点进入 execute**，USER 末节点视为不可执行。
2. **`DEPT_MANAGER / EMP_MANAGER` 等角色型末节点**：`assigneeRole` 存的是角色 key，与 `getRoleKey` 一致即可正常放行。
3. **自动执行 / 交接单**：`finalNodeRole=null` 不进 execute；`confirmHandover`（离职）不经 execute，均不受影响。
4. **测试调整**：
   - 修改断言硬编码 `finalNodeRole=ASSET_MANAGER` 的用例（如 `tests/approval-engine.test.ts`），改为"末节点配置的角色"。
   - `approval-execute` 相关测试：核实"角色不匹配即失败"逻辑仍成立；新增"某个角色账号执行该角色为末节点的单成功"用例。
   - 删除/改写依赖 `ensureAssetManagerFinalNode` 不变式的用例。

## 验证（端到端）

1. settings/workflows 把 ASSET_UPGRADE 末节点改为 `assigneeType=ROLE, assigneeRole=DEPT_MANAGER`（或任一非 ASSET_MANAGER 角色）。
2. 发起升级申请 → DEPT_MANAGER 账号审批通过 → 该账号登录 execute 页能看到并能执行（改配件 + 释放预占 + 写 executedAt）。
3. 原 ASSET_MANAGER 账号登录 execute，看不到该单。
4. 回归：报废/退回（finalNodeRole=null）不进入 execute；离职单仍走交接对账，不受影响。
5. 跑相关单测：`npm test -- approval`（或仓库现有测试命令）确认通过。
