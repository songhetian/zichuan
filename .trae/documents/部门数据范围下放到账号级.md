# 部门数据范围从「角色级」下放到「账号级」

## Context（背景与目标）

现状：部门数据范围存放在**角色**上（`Role.departmentScope: ALL|SPEC` + `RoleDepartment` 关联表），由「设置→角色权限」的编辑弹框配置。

问题（用户反馈）：
- 一个系统可有 20+ 部门，若想让每个部门各有主管、各自只看本部门，由于范围绑在角色上，**所有共享该角色（如 DEPT_MANAGER）的账号只能共享同一份部门范围**，无法做到同角色内每个账号各自限定部门。
- 「全部」默认对拥有 `asset.manage` 的角色=不限，一旦给部门主管加了 `asset.manage` 又忘设 SPEC，即有越权面。

已与用户确认的方向（方案 B）：**把部门数据范围从角色级下放到账号级**。
- 范围编辑界面：移到「设置→用户管理」，每个账号可单独选「全部 / 指定部门」。
- 存量处理：迁移时把原角色级 SPEC 的范围**继承**给每个拥有该角色的账号（同一角色下账号继承同一份），再在账号级微调。

## 涉及的文件与改动

### 1. 数据模型 `prisma/schema.prisma`
- `Admin` 增加：`departmentScope String @default("ALL")` + 关联 `departmentLinks AdminDepartment[]`。
- 用新模型 `AdminDepartment`（`adminId + departmentId`，`@@id([adminId, departmentId])`，onDelete Cascade）**取代** `RoleDepartment`。
- `Role` 移除：`departmentScope`、`departments RoleDepartment[]`。

### 2. 迁移（两步，保证存量继承）
采用**先加后删**两步迁移 + 幂等回填脚本，避免丢数据：
1. **迁移 A（增量）**：给 `Role` 加无变更、给 `Admin` 加 `departmentScope` 与 `AdminDepartment` 表（此时旧表仍在）。
2. **回填脚本** `scripts/migrate-scope-to-account.ts`（tsx，幂等）：遍历每个 `Admin`，按其 `role` 若 `role.departmentScope==='SPEC'` 则把该 admin 的 `departmentScope` 置 `'SPEC'` 并插入对应 `AdminDepartment` 行；否则保持 `'ALL'`。
3. **迁移 B（删列）**：删 `Role.departmentScope`、`Role.departments` 关系、`RoleDepartment` 表。

沿用仓库惯例：开发库 `npm run db migrate`（prisma migrate dev），测试库 `npm run db test:init`。

### 3. 权限解析 `src/lib/permissions.ts`
- 把 `resolveRoleDepartmentScope(userId)` 重命名为 **`resolveDepartmentScope(userId)`**（或保留签名保持不变，仅改内部实现读账号级范围），仍返回 `"ALL" | number[]`：
  - 账号拥有 `system.account.manage` → 强制 `"ALL"`（防锁死）。
  - 否则读 `admin.departmentScope`：`'SPEC'` → `admin.departmentLinks` 的部门 id 列表；否则 `"ALL"`。
- 更新所有调用 `resolveRoleDepartmentScope` 的位置（见第 4~7 点）。

### 4. 角色写入/读取 `src/actions/admin.actions.ts`
- **删除** `setRoleDepartmentScope(roleId, …)`，新增 **`setAccountDepartmentScope(adminId, { scope, departmentIds })`**（沿用 `guardAccountManage` 守卫，校验部门存在；拥有 `system.account.manage` 的账号禁止设 `SPEC`，理由同原超管限制）。
- `getRoles()` 不再返回 `departmentScope / departmentIds`（这两项改由账号携带）。
- 新增读取账号范围的实现（供用户管理页回显）：`getAccounts` 或现有用户列表 action 附带 `departmentScope` + `departmentIds`，并返回全部部门列表供勾选。

### 5. 资产范围 `src/actions/asset.actions.ts`
- `resolveAssetScope`（L299-318）改为调用新解析器；`asset.manage` 分支的部门过滤逻辑不变（`employee.departmentId in scope`）。

### 6. 部门员工操作 `src/actions/department-employee.actions.ts`
- `resolveAllowedDeptIds`（L87-102）：把 `admin.role.departmentScope==='SPEC'` + `admin.role.departments` 改为读 **账号级** `admin.departmentScope` + `admin.departmentLinks`；`managedDepartments` 兜底逻辑保持不变。

### 7. 审批可选设备 `src/lib/approval-scope.ts`
- `getUpgradeAssetOptions`（L19-23）与 `getApprovalDelegationTargets`（L60-62）里对 `role.departmentScope / role.departments` 的引用全部改为账号级范围。

### 8. 前端-角色权限 `src/app/(main)/settings/roles/roles-client.tsx`
- 从角色编辑弹框**移除**整块「数据范围」（“全部/指定部门”单选 + 部门多选，L407-461 附近）。角色权限页回归纯权限点配置。
- 同步清理该文件里 `scope / scopeDeptIds / setRoleDepartmentScope` 相关 state 与 `openEdit` 里回填逻辑；`RoleRow` 类型去掉 `departmentScope / departmentIds`。

### 9. 前端-用户管理 `src/app/(main)/settings/users/*`
- 在用户（账号）编辑里新增「数据范围」区块（复用 roles-client 里被移除的单选+部门多选 UI 结构）：`全部 / 指定部门` + 部门网格勾选，保存调用 `setAccountDepartmentScope`。
- `users/page.tsx`（服务端）读取角色与部门授权后，把账号列表（含 `departmentScope`/`departmentIds`）和全部部门列表传给客户端。

### 10. 种子与初始化 `prisma/seed.ts` / `src/lib/org-bootstrap.ts`
- 检查是否有对角色 `departmentScope` 的引用，改成账号级默认（通常不配即 `'ALL'`）。

### 11. 测试随迁（tests/）
- 搜索并改写依赖 `setRoleDepartmentScope` / `role.departmentScope` / `RoleDepartment` 的用例，改用 `setAccountDepartmentScope` / 账号级范围。可能的文件：`tests/approval-engine.test.ts`、`tests/approval-execute.test.ts`、以及其他 admin/department 相关测试。

## 复用点
- 账号已通过 `Admin.employeeId` 关联员工（`schema.prisma` L282）。
- 部门负责人机制 `employee.managedDepartments` 保留为「非 SPEC 时按主管管辖部门」的兜底，无需改动。
- 前端部门多选用现有 `SearchableSelect` / `Checkbox` 网格即可。

## 风险与处理
1. **防锁死**：拥有 `system.account.manage` 的账号禁止设为 SPEC（否则超管自身范围被锁）。沿用原 `setRoleDepartmentScope` 对 SUPER_ADMIN 的限制逻辑。
2. **存量继承**：回填脚本幂等，重复运行不产生重复行（按 `@@id` upsert）。
3. **孤儿部门**：角色下限制部门的部分权限点不受影响；权限点 `dept.data.view` 语义不变。
4. **命名冲突**：与 `RoleDepartment` 表名类似的索引/迁移名避免冲突，回填脚本在迁移 A 之后运行。

## 验证（端到端）
1. `npm run db migrate` 建迁移 → 回填脚本跑通 → 再跑删列迁移；`npm run db test:init` 重建测试库。
2. 用 `setAccountDepartmentScope` 给账号 A 设 SPEC=[部门1]，账号 B 保持 ALL：登录两账号分别打开资产列表，A 只见部门1 资产、B 见全部。
3. 两个 DEPT_MANAGER 账号共享同一角色，但各自可被设不同部门范围（验证方案 B 核心诉求）。
4. 升级发起可选设备 / 主管代申/部门员工操作，跟随账号级范围变化。
5. 回归相关单测：`npx vitest run tests/approval-engine.test.ts tests/approval-execute.test.ts --no-cache` 通过。
